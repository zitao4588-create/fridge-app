## 2. 第一性原理：这个产品必须把什么做好

用户使用冰箱小雷达，是为了快速知道“家里有什么、先用什么、还要不要买”，并让家人看到可信的一份库存。

因此价值链是：真实食材容易录入 → 打开即能看见可信库存 → 用掉后容易更新 → 需要时提醒 → 下一次仍愿意维护。

最小必要复杂度包括：个人/家庭归属、服务端权限校验、数量更新与撤销一致性、可靠日期、失败恢复。可选复杂度包括：OCR、照片附件、装饰动画、评分与非核心页面。不能为了减少行数把两类一起删除。

建议成功指标为“首条真实食材保存后，7日内在另一天再次进行保存、编辑或消耗的账号数”；同时观察首条保存成功率和完成时间。样板食材、测试账号和单纯打开页面要单独标识，暂时无法区分的部分写未知。

停留时间越长不一定越好：录入更慢、页面等待更久也会拉长时长。次日留存对低频库存工具只是参考，应结合7日有效维护行为，不能用小样本日环比直接决定产品失败或成功。

## 3. 重新解释截图和原任务

### 3.1 三种问题应分开

1. 数据接口问题：原任务9月1日记录的170次请求中119次成功、51次`9900030`；没有持续平台错误。这只能说明当时数据拉取总体完成。
2. 用户体验问题：截图明确出现冷启动、页面耗时、页面错误比例、白屏比例告警。它们没有被上面的接口核验排除。
3. 业务送达问题：原任务记录8月1–12日提醒61/61成功；8月13日至9月1日0/165成功，错误指向`40164 invalid ip`。这是当时的业务发送失败，不是9月8日实时结论。

原任务“真正故障是提醒链路”的表述应收窄为“提醒故障已有发送记录证据；客户端性能问题仍需单独核查”。

### 3.2 截图能支持什么

- 8月23日页面错误比例上升10.03个百分点；8月26日页面错误和进入白屏占比上升，应优先取错误详情。
- 冷启动告警在8月20日、22日、24日、30日、31日和9月4日多次出现；9月4日摘要报告上涨313%。需要性能专项，不能只作为推广指标波动处理。
- 不知道313%的原始耗时、启动次数和分布，所以不能据此断定代码膨胀、云函数冷启动或某次发布是根因。
- 所有完整摘要均显示平台收集反馈0条；这不等于无问题，原任务还记录了23条用户评论内容。
- 截图不是连续25天完整报表。不能将各日增长率累加，也不能把缺失日当正常。

### 3.3 旧增长结论需要更新

原任务截至8月28日的窗口曾显示新增24对49；后续截至8月31日的窗口变成新增46对43，访问人数日107对97。两者都是各自历史窗口，不能继续用“-51%”代表当前趋势。

9月1日月报记录8月累计访问人数日378、打开709次、新增178、页面访问5613、期末累计用户438。人数日不是月去重人数。最近窗口新用户D1为15.8%对20.9%，但仍缺首条保存漏斗和测试流量拆分，不能断言“低留存一定因缺OCR”。

## 4. 应先修复的具体问题

### S1：家庭撤销会覆盖另一位成员的消耗（建议P1）

源码位置：[familyInventory/index.js](/Users/qzt/Developer/projects/fridge-app/cloudfunctions/familyInventory/index.js:554)。

本轮实际源码在合成内存数据库中的结果：初始数量3 → A用掉1 → B用掉1 → 当前1 → A撤销 → 变回3。正确结果应为2，或者明确拒绝发生冲突的撤销。当前文件和Git HEAD均复现。

原因：撤销使用事件中的旧数量整体写回；虽然使用了事务，但没有在事务中核对当前食材状态及撤销记录的新状态。单纯“有事务”并不保证不会覆盖他人更改。

最小修复：在事务内重新读取食材和撤销记录，约束一次撤销与冲突行为；不得覆盖B的后续操作。移出库存后撤销、重复点击撤销也要验证。上线是否已有人受影响，尚无证据。

### S2：家庭权限失败后详情内容仍残留（建议P1）

源码位置：[首页加载错误处理](/Users/qzt/Developer/projects/fridge-app/pages/index/index.js:280)、[详情弹层](/Users/qzt/Developer/projects/fridge-app/pages/index/index.wxml:205)。

本地执行结果：权限检查未结束时旧库存仍显示；返回权限无法确认后，列表已清空，但`foodDetailVisible`仍为true、`selectedFood`仍保留。模板仍会展示名称、日期和备注。

最小修复：把家庭权限状态同步用于列表、详情、拖动对象、撤销入口等所有派生状态；权限未知或撤销时隐藏家庭内容。个人缓存可以采用不同策略。这里发现的是前端旧内容残留，不等于证实服务器允许越权读取新数据。

额外核验：没有家庭本地缓存时，读取服务会直接进入个人路径；需覆盖“已有家庭成员在新设备首次打开”的场景，防止空库存被误认为数据丢失。

### S3：提醒标记可重试，但同一天会直接跳过（建议P1）

源码位置：[提醒去重判断](/Users/qzt/Developer/projects/fridge-app/cloudfunctions/sendExpiryReminders/domain.js:17)、[发送循环](/Users/qzt/Developer/projects/fridge-app/cloudfunctions/sendExpiryReminders/index.js:391)。

`hasDailySummaryRecord`只判断类型和日期，不区分sent、failed。合成`failed + retryable:true`记录返回true，因此修复网络后同日再调用也会被去重跳过。当前测试通过不能证明重试闭环成立。

最小修复：区分发送成功、明确拒绝、可重试失败和发送结果未知；只在可确定的情况下补发，避免把接口已接受但记录失败的情况盲目重发。保留按账号/日期防重复的语义，补同日失败恢复和重复触发测试。

### S4：不能直接执行“删Secret切回云调用”

原任务提出切回`cloud.openapi`，但[BUG_NOTES.md](/Users/qzt/Developer/projects/fridge-app/BUG_NOTES.md:2289)记录：6月定时触发曾报`invalid wx openapi access_token`，换成服务端接口后才于6月17日取得自动实收。它是历史环境证据，不是平台永久限制，但足以阻止无验证回切。

下一步先只读核验当前环境、发送模式、触发身份、出口、白名单和脱敏错误分类；然后在授权测试接收账号下证明候选模式的手动与定时实收。若当前云调用能可靠完成定时发送，才选择简化到云调用；否则评估官方支持的稳定出口或受支持发送方案及成本。不要追着动态出口IP逐个加白名单。

原任务记录了两份Secret曾进入工具输出。是否已轮换未获实时确认；若仍有效，应作为独立安全处置优先处理。不得重复取值、回显或把轮换当作本轮已授权操作。

## 5. 是否需要全面代码简化

结论：做定点简化，暂不做全面重写、框架替换或数据库迁移。

| 候选 | 已读证据与价值 | 建议 |
|---|---|---|
| 删除无用启动调用 | `app.js`每次启动调用`getOpenId`；全项目运行JS搜索未找到`globalData.openid`业务读取者 | 移除客户端调用及无用状态即可；先不删除云函数。它是非阻塞请求，不能承诺删掉就解决冷启动 |
| 手动表单摆脱旧识别模块 | 表单仅调用`parseService`的日期计算和分区建议，却引入664行历史识别、Mock、缓存、日志代码 | 将两项纯本地能力迁到已有日期/食材规则模块，移除表单对此旧模块的依赖；旧文件可先保留 |
| 缩短家庭读取链 | 首页先`getFamilyState`再`listItems`；前者读取家庭成员列表，迁移状态下甚至尝试迁移写入 | 库存页采用轻量、服务端验权的读取结果；成员详情按需加载。不能删权限校验，也不能把`getFamilyState`当纯只读API |
| 请求进行中共享 | 10秒完成结果缓存存在，但无进行中请求合并；首页/日历切换可重复请求 | 按个人/家庭范围与权限状态合并并发读取，防止旧请求覆盖新状态 |

| 拖动更新 | 每次touchmove调用setData更新坐标与餐盘状态 | 测量拖动卡顿，必要时节流并保证松手位置准确；与启动故障分开 |

| 历史AI云函数 | `generateRecipes`、`parseFoodImage`、`parseBarcode`合计3417行，但`cloudfunctions`已排除客户端上传 | 后续独立归档/退役评估；删这些代码不是已证实的客户端提速措施，云端删除单独决策 |
| 文档与工具目录 | 多份文件同时保留C0/C1/C2历史；上传配置没有显式列出`.codex`排除 | 保留一页当前状态和历史链接；核验实际预览文件清单。未证实`.codex`已进入发布包 |

本轮用实际首页数据构建逻辑和合成食材测得，单次完整更新序列化大小：20条26,833字节、100条92,116字节、500条419,316字节。500条中单独`allItems`占204,391字节，分区又含500个完整食材对象。这是数据冗余证据，不是手机耗时测试，也不是实际用户库存分布。

可保留的结构：原生小程序、CloudBase、现有个人/家庭数据模型、轻量服务模块、非生成式候选层和必要的图片状态记录。前后端都校验输入有其边界用途，不应为“去重”移除服务端校验。

## 6. 性能专项该怎样验收

先取得相同日期窗口的绝对耗时、样本数、P50/P95（若后台提供）、页面错误/白屏分子分母、设备/微信/基础库/版本、进入场景和错误堆栈。取不到分位数就保留原始计时分布，不用均值代替。

把用户看到可用库存的等待分解为：包下载与初始化、页面创建、身份/家庭确认、库存查询、数据传输和渲染。小程序冷启动与云函数容器冷启动不是同一个指标。CloudBase官方也将云函数冷启动拆分为容器和用户代码初始化，不能仅凭前端告警定位到容器。[官方冷启动说明](https://docs.cloudbase.net/recipes/optimize-cloud-function-wechat-miniprogram)

建议首批覆盖：iPhone/Android各一台，普通网络/弱网，个人/家庭，冷启/热启，20/100/500条合成库存；异常测试包括权限移除、读取超时、恢复网络、打开详情后切后台。性能时间在相同设备、网络和数据条件下前后对照；不能用Mock耗时代替。

放行条件：所有确定可复现的权限残留、数量覆盖、白屏和阻断性失败已关闭；错误有可恢复入口；真实流程完成；性能改动有前后实测且无明显回退。目标耗时应在取得绝对基线后定，不现在编造一个“提升50%”承诺。

## 7. 已准备好的V3如何处理

V3保留已有成果，但应分为三个可独立验收的内容包：

| 内容包 | 当前事实 | 调整 |
|---|---|---|
| A 稳定性 | 家庭权限刷新、朋友圈入口收敛、家庭结果提示、加载重试、原生反馈已有实现 | 前移到2.1；修完S1/S2/S3并做真实验收，不等待OCR |
| B 快速录入 | 相机/相册、本地预览、上传、OCR、候选确认、进入最终表单、手动兜底已接线；客户端两个开关为true | 单独作为3.0候选；验证用户是否更快完成保存 |
| C 保留用户照片 | 明确选择后绑定正式食材；默认不保留；临时会话清理已有实现与历史实测 | 增加正式附件删除/替换/用尽/撤销/家庭迁移验收，达不到则先不开“长期保留” |

图片生命周期存在一个具体缺口：当前`retained`会话明确拒绝临时清理，而个人/家庭删除和用尽路径未发现正式附件回收接线。应定义保留照片何时删除、撤销窗口如何保护照片、换照片后的旧对象如何回收；不能把“临时图24小时清理”视为覆盖了长期附件。现有源码不足以证明线上已有孤儿文件，本轮未查真实存储。

旧真实样本证据：20张公开图均成功调用供应商，但当时没有可采用日期；另12张日期图只有1张产生完整日期候选；7月26日公开牛奶图端到端返回0个可靠名称/日期。这些样本不代表中国家庭包装的今天准确率，但说明还没有足够帮助度证据。

### 改写OCR放行条件

保留原计划“至少20组代表性样本、14/20有效帮助”的最小试验要求，但不要只看有没有字段。增加：

- 同一类任务与手动录入比较端到端保存时间、点击次数、修正字段数和失败后恢复成本，减少练习顺序造成的偏差。
- 分开记录名称、生产日期、保质期、到期日及日期冲突；猜到品类不能算日期识别成功。
- 正确候选必须让用户少填或更快，不能多走拍照、等待、确认后还完整重填。
- 错日期不得自动写入；无候选、网络失败和清理待处理时，始终能进入安全的手动路径。确认页已有“待清理仍转手动”分支，要保留并验证，不应因界面合并丢失。
- 完整隐私说明、第三方处理、服务类目按当前账号核验；不恢复“个人主体一律不能OCR”的无证据判断。
- 增加每次有效保存的OCR调用成本、重复调用量和失败率，费用上限由届时实际方案决定。

20组只适合作为首轮可用性筛查，不是统计意义上的准确率认证。建议试验结果明显胜过手动才放行；仅“14/20出现一个正确字段”不足以自动发布3.0。

## 8. 版本顺序与可执行任务

建议顺序：

```mermaid
flowchart LR
  A[确认线上状态与安全处置] --> B[2.1 稳定性与定点简化]
  A --> C[独立恢复提醒链路]
  B --> D[双账号与真机验收]
  C --> E[手动与定时实收及观察]
  D --> F[2.1 发布候选]
  F --> G[小规模观察与有效维护数据]
  G --> H[3.0 快速录入帮助度决策]
```

## 9. 新功能取舍

需求证据来自原任务两篇帖子共38条评论、23条用户内容；这是当时已完整读取的历史样本，本轮没有刷新，不能当普遍需求比例。

| 功能 | 判断 |
|---|---|
| 清空全部移出首页 | 纳入稳定版的低频数据管理入口，保留能力和确认，避免高频操作面上的误触压力 |
| 家庭邀请路径说明/问题反馈 | 完成现有闭环，不建新的引导系统或客服后台 |
| 多选用掉 | 下一项新增能力的优先候选；先修单条撤销一致性，再定义逐条结果与部分失败重试，不先接自由文本AI |
| 隐藏分区/自定义显示名 | 另一个候选；沿用稳定分区键，隐藏后库存仍可访问；先决定个人偏好还是家庭共享偏好 |
| 自己上传照片 | 不重复开发现有上传；先证明长期照片管理可闭环。若只为自定义缩略图，也不应强迫使用OCR |
| 提前1/3/7天提醒 | 现有送达和授权价值成立后再试；不扩到提前数月、药品或护肤品 |
| 年/月剩余时间文案 | 可与相关日期显示修复同批做，不为它改数据模型或单开大版本 |
| 菜谱、生成图、健康余额、重量单位、多冰箱、支付会员、UGC | 继续后置；当前没有证据证明这些比库存可信和维护省事更急迫 |

产品界面是否要减少菜谱占位Tab、合并确认页，可以在后续静态方案中讨论。本轮不建议为了“全面简化”同时更换首页布局、手势和导航，避免性能与交互变化无法归因。

## 10. 上线后的判断与收口

新版本先做72小时故障观察，再进入小规模用户验证；小样本没有错误不能证明线上零故障。原计划20–50名种子用户可作为招募上限，先保证能观察真实首条保存和后续维护，不按曝光量扩张。

提醒按“有可用授权且有应提醒食材的目标、实际尝试、接口接受、明确拒绝、失败、结果未知”分别计数。API接受率与用户实收不是同一指标；没有授权不算发送失败。保留一次人工实收、一次定时实收和7个完整自然日观察。历史99%目标只能在明确定义分母后使用，样本少时直接报告分子/分母。

本轮不替换`TODO.md`、`DECISIONS.md`或旧执行方案，不改业务代码、不提交、不部署、不发布。本报告与纯本地复现材料是交付产物。后续若采纳，第一批实施以T0–T4为范围，不默认启动所有新功能。
