## 1. 一句话结论

后续不再以“增加更多功能”为主线，而按以下唯一顺序推进：

> 恢复提醒信任 → 冻结可恢复候选 → 完成双账号与真机验收 → 用 20 组真实样本决定发布 `3.0.0` 还是 `2.1.0` → 静默上线 → 小规模种子用户 → 微信主阵地推广 → 用两周数据决定 `3.1.0`。

任何阶段未通过，都不得用后续阶段的工作掩盖或绕过。

## 2. 当前事实基线

### 2.1 已确认

- `2.0.0` 已于 2026-07-14 正式发布，当前等级为 C3；线上核心回归和真实用户验证尚未完整闭环。
- 当前 V3 工作区包含 v2.1 五项稳定性改进、一图一件快速录入、非生成式 OCR 候选、人工确认、失败回退、临时图片清理和原生反馈入口。
- `CAPTURE_FEATURE_ENABLED` 与 `RECOGNITION_FEATURE_ENABLED` 当前均为 `true`；正式 `captureImageSession` 和 `extractFoodCandidates` 已部署。
- 当前本地复跑结果：19 个测试文件、635 条断言全部通过；`git diff --check` 通过。
- V3 尚未形成正式提交检查点，尚未上传当前体验版、提审或发布；工作区包含大量既有修改和未跟踪文件。
- V3 双账号、真机、精确压缩包体、微信后台服务类目和完整隐私指引仍未完成最终验证。
- 最近完整 7 日与前 7 日相比：新增用户 24 vs 49（-51.0%），访问人数日 79 vs 97（-18.6%），页面访问 1,346 vs 1,305（+3.1%），人均使用时长 282.7 秒 vs 192.3 秒（+47.0%）。
- 最近 14 日新用户来源行中，搜索占 75.3%，分享占 13.7%。
- 近 7 日到期汇总提醒送达为 0/56；8 月 13 日起连续失败，现有脱敏错误一致指向微信接口 IP 白名单或实际出口不匹配。

### 2.2 明确推断

- 当前主要矛盾不是功能不足，而是新增收缩、首次价值不清、提醒失信和缺少可归因漏斗。
- 留下来的用户使用更深，但不能据此推断新增用户质量、真实用户规模或 V3 拍照录入一定有价值。
- 搜索是当前最明确的获客入口，但还没有证据证明搜索用户的激活或留存优于分享用户。

### 2.3 仍待核查

- 真实用户与开发/测试流量的准确拆分。
- 新用户第一次会话是否成功保存第一条真实食材。
- 真实家庭包装下 OCR 候选能否实际减少输入。
- 两账号移除、旧邀请、冷启动、旧缓存和家庭写入失败是否全部符合权限预期。
- 当前账号后台的服务类目、隐私保护指引、第三方处理说明和审核口径。
- 提醒修复后的真实手动送达、定时送达和连续运行稳定性。

## 3. 北极星目标与版本原则

### 3.1 北极星目标

不是“下载量”“曝光量”或“库存记录总数”，而是：

> 新用户成功保存第一条真实食材后，在 7 日内至少另一天再次保存、编辑或消耗食材的账号数。

在该指标尚不能直接计算前，使用以下四组代理信号：

1. 新用户 D1 和完整 7 日访问趋势。
2. 新建库存记录、更新记录和来源字段分布。
3. 拍照会话启动、确认、转手动、保存和清理状态。
4. 提醒授权与真实送达结果。

### 3.2 版本原则

- 线上故障与新功能解耦；提醒能独立修复就不等待 V3。
- 已经开发完成不构成发布理由；真实帮助度、安全、回退和可测量性才构成发布理由。
- `v2.0.x` 和 `v3.0.x` 只修 P0/P1，不夹带新功能。
- 没有一个版本因为排期到了而必须发布；只有闸门通过才进入下一步。
- 提交、推送、云端配置、上传体验版、提审、正式发布和推广发布是六个独立授权点。

## 5. E1：恢复到期提醒

### 5.1 目标

把“函数能运行”提升为“真实用户确实收到”，恢复产品最基础的信任承诺。

### 5.2 执行任务

- [ ] 只读记录当前正式 `sendExpiryReminders` 配置字段名、触发器、最近失败数和脱敏错误类别；不得输出真实值。
- [ ] 核对 CloudBase 函数实际公网出口与微信公众平台 IP 白名单是否一致。
- [ ] 如只需修改白名单或出口配置，形成精确变更前后清单并单独请求云端配置授权。
- [ ] 如需改代码，只允许修改提醒发送、重试和可观测性相关文件，不混入 V3 客户端功能。
- [ ] 使用一个已授权测试账号执行一次真实手动发送；只记录时间、模板类型、`errcode/errMsg` 和是否实收。
- [ ] 等待下一次定时任务，记录一次真实自动实收。
- [ ] 修复后观察 7 个完整自然日，按 `sent ÷ attempts` 计算送达率。

### 5.3 通过标准

- 一次手动实收成功。
- 一次定时实收成功。
- 失败记录可重试，不因旧失败被永久跳过。
- 连续 7 日送达率不低于 99%；样本不足时报告精确分子/分母，不用百分比掩盖。

### 5.4 停止条件

- 需要新增或轮换 Secret、发送给非测试用户、扩大消息范围或改变家庭成员提醒语义时立即停止。
- 白名单/出口修改会影响其他生产服务时立即停止并列出影响面。
- 未取得真实接收证据，不得宣称提醒已恢复。

### 5.5 版本归属

- 仅配置变更：记录为运维事件，不创建客户端版本。
- 涉及客户端、隐私或审核文案：发布 `2.0.1`，只带 P0/P1 修复。

20 组样本逐组记录：

- 是否返回真实候选。
- 至少一个候选是否正确。
- 是否实际减少用户输入。
- 是否出现误导性日期或名称。
- 是否能完整修改或转手动。
- 是否最终只保存一条用户确认的食材。

- 至少 14/20 组有一个正确且能减少输入的候选。

- 0 次自动写库存。
- 0 次越权访问。
- 0 个验收结束后仍未收口的孤儿会话。

## 9. E5：微信后台与隐私合规

### 9.1 必需证据

- 当前账号服务类目截图，遮蔽 AppSecret、手机号和无关身份信息。
- 当前用户隐私保护指引全文或关键页截图。
- “收集你选中的照片或视频信息”的实际声明状态。
- 第三方腾讯云 OCR 的处理目的、数据类型、处理地域、保存/问题数据、共享/转委托、撤回和联系方式说明。
- 审核版本说明、功能截图和实际入口的一致性核对表。

### 9.2 文案边界

允许：

- “拍照或从相册选择一张食品包装图片。”
- “系统给出非生成式候选，由你确认和修改后才保存。”
- “识别失败可直接转手动填写。”
- “临时图片按当前说明清理；明确保留后才作为食材附件。”

禁止：

- “自动准确识别食品和过期日。”
- “AI 自动管理冰箱。”
- “图片绝不经过第三方。”
- “任何情况下 24 小时绝对物理删除。”
- 把腾讯云通用 OCR 整体准确率当作食品包装字段准确率。

### 9.3 停止条件

- 后台类目或隐私声明与实际入口不一致。
- 第三方处理说明无法准确告知用户。
- 审核要求恢复生成式 AI、支付、登录、手机号或公开 UGC。

## 11. E7：体验版、提审和发布

### 11.1 每次操作前必须展示

- 目标 AppID 脱敏标识。
- 分支、HEAD 和工作区状态。
- 版本号与版本说明。
- 精确包体。
- 本次动作：预览、上传体验版、提交审核或正式发布。
- 已通过和仍未验证项目。

### 11.2 操作顺序

1. 生成预览二维码。
2. 两账号扫描同一预览并完成 E4。
3. 上传体验版。
4. 用体验版再回归一次核心路径。
5. 用户单独授权后提交审核。
6. 回读审核状态；提交成功不等于审核通过。
7. 审核通过后展示正式版本、目标环境和发布说明。
8. 用户再次单独授权后正式发布。
9. 回读线上版本页和真实小程序，确认版本确实生效。

### 11.3 回滚准备

- 保留上一正式版本信息和当前发布候选检查点。
- 准备关闭快速录入/识别闸门的补丁路径。
- P0：隐私、越权、数据损坏、白屏、核心读写失败时立即停止推广并进入热修。
- P1：提醒持续失败、快速录入无法回退、家庭状态大面积错误时停止扩量并在 24 小时内决定修复或回退。

## 12. E8：发布后 72 小时静默观察

- 不做付费投放。
- 不建立用户群。
- 不宣称 OCR 准确率、节省时间或减少浪费金额。

### 12.2 每日观察

- P0/P1 反馈和原生反馈后台。
- 提醒 attempts、sent、failed 和错误类别。
- 新建/更新库存记录。
- 拍照会话启动、确认、转手动、保存、清理和失败状态。
- 家庭邀请、加入、移除和失败事件。
- WeData 新增、访问、页面、来源和留存。

### 12.3 通过标准

- 72 小时内无未处理 P0/P1。
- 手动录入始终可用。
- 提醒保持真实送达。
- 图片会话无未解释积压。
- 没有隐私、权限或数据损坏信号。

## 13. E9：20–50 名定向种子用户

### 13.1 目标人群

- 有真实家庭冰箱管理需求的人。
- 愿意在一周内至少使用两次。
- 能对“第一次添加是否顺畅、提醒是否可信、家庭共享是否易懂”给出具体反馈。

不以泛 AI 兴趣用户或纯开发围观用户作为产品激活样本。

### 13.2 单一邀请话术

> 我做了一个微信小程序「冰箱小雷达」，用来记录冰箱食材和到期时间。现在想找少量真实家庭用户试一周，重点看第一次添加、到期提醒和家庭共享是否真的省事。可以直接微信搜索“冰箱小雷达”。

若发布的是 `3.0.0`，可增加：

> 拍包装图只会给出候选，必须由你确认后才保存；不想拍照也可以一直手动填写。

### 13.3 成功标准

- 不用“加入人数”作为最终成功。
- 记录首条保存、第二次使用、反馈问题和提醒实收。
- 种子阶段结束时能够回答：用户为何留下、为何离开、最大阻塞在哪一步。

## 15. E11：`3.1.0` 决策规则

连续两周数据后，只允许选择一个主瓶颈：

| 最大瓶颈 | 允许的 `3.1.0` 方向 | 暂不做 |
|---|---|---|
| 搜索流量少 | 名称、简介、搜索词和内容匹配 | 多平台付费扩量 |
| 首条保存率低 | 空状态、第一步引导、字段默认与表单摩擦 | 新页面和复杂 onboarding |
| 拍照候选无帮助 | 改入口定位、样本范围或继续关闭 | 用生成式 AI 猜测字段 |
| 提醒影响复访 | 授权时机、文案和稳定性 | 复杂提醒设置中心 |
| 家庭邀请低 | 邀请说明和失败恢复 | 更多角色、群聊和社交功能 |
| 个人消耗不可观测 | 最小聚合事件设计 | 大型埋点平台 |

没有明显瓶颈，或样本不足时，不立项 `3.1.0`。

## 16. KPI 与统计口径

| 层级 | 指标 | 定义 | 当前基线 | 下一目标 |
|---|---|---|---|---|
| 北极星 | 7 日复访激活账号 | 首条保存后 7 日内至少另一天保存、编辑或消耗 | 当前不可直接计算 | 先建立两周基线 |
| 激活 | 首轮首条保存率 | 首轮会话成功保存第一条食材 ÷ 新用户 | 当前不可连接 | 先补最小口径 |
| 留存 | 新用户 D1 | 次日仍活跃新用户 ÷ 新用户 | 12.5%（3/24） | 滚动 14 日样本 ≥50 后达到 ≥20% |
| 可靠性 | 提醒送达率 | `expirySummary sent ÷ attempts` | 0/56 | 修复后连续 7 日 ≥99% |
| V3 帮助度 | 有效候选率 | 正确且减少输入的样本 ÷ 20 | 未验证 | ≥70% |
| V3 漏斗 | 拍照确认保存率 | 拍照路径最终保存 ÷ 拍照启动 | 不可计算 | 上线后建立基线 |
| 安全 | 越权/孤儿会话 | 越权次数与未收口会话数 | 真机未验证 | 验收为 0 |

统计规则：

- WeData 使用完整等长周期和 Asia/Shanghai 时区。
- “访问人数日”不当作去重周活。
- 来源行占比不当作跨来源去重用户占比。
- CloudBase 账号、库存和事件不与 WeData 用户数直接相加。
- 单周新用户样本小于 30 时，只报告分子/分母和方向，不作确定性因果结论。
- 正式环境尚不能可靠拆分真实与测试流量，所有对外数字必须标注这一限制。

## 18. 角色分工

### Codex

- 代码和文档只读盘点、候选归类、局部实现、自动化验证和证据汇总。
- 每个外部动作前展示目标和影响，执行后回读真实状态。
- 不记录或输出 Secret、Token、OPENID、家庭 ID、邀请口令、OCR 原文和私人图片。

### 用户

- 提供两个真实微信账号/设备的操作条件。
- 人工确认微信后台服务类目和隐私指引截图。
- 完成真实订阅授权并确认是否收到测试消息。
- 对 commit、push、云端修改、上传、提审、发布、外发和付费逐项授权。

### 平台

- 微信审核、消息送达、CloudBase 调度和内容平台分发均属于外部状态；提交成功不能替代审核通过，任务触发不能替代用户实收。

## 20. 整体完成定义

本总方案只有同时满足以下条件才算完成：

- 提醒真实送达恢复并稳定观察。
- V3 候选有可恢复检查点，且无本地杂项或敏感信息混入。
- 自动化、本地编译、精确包体、双账号、真机、弱网、分享、反馈和 OCR 样本验收均有证据。
- 类目、隐私、第三方处理说明和审核材料一致。
- 根据帮助度发布 `3.0.0` 或 `2.1.0`，并完成线上回读。
- 72 小时静默观察无未处理 P0/P1。
- 20–50 名定向种子形成可解释的激活与复访基线。
- 完成两轮小规模内容实验，只按激活和留存决定是否扩量。
- `3.1.0` 只针对一个已验证的最大瓶颈，或明确决定暂不立项。

## 21. 立即可执行的第一批

在不需要外部写入的前提下，下一批按以下顺序执行：
